# SmartDuka Mobile API v1

All endpoints return `{ "data": ... }`; list endpoints additionally return bounded pagination metadata. Errors use `{ "error": { "code", "message", "fields?" } }`.

Authentication is the existing Firebase identity token in `Authorization: Bearer <Firebase ID token>` (or an existing SmartDuka session token for server-to-server compatibility). Identity, active status, vendor membership, and permissions are resolved on the server for every protected call.

Implemented transport adapters: public catalogue (`/categories`, `/products`, `/products/:id-or-slug`, `/shops`, `/shops/:slug`, `/search`); customer (`/me`, `/wishlist`, `/checkout`, `/orders`, `/orders/:id/payment-status`, `/devices`, `/marketplace-reports`); vendor (`/vendor/context`, `/vendor/dashboard`, `/vendor/analytics?period=TODAY|7D|30D`, `/vendor/orders`, `/vendor/products`, `/vendor/products/:id`, `/vendor/inventory`, `/vendor/inventory/adjustments`, `/vendor/shop`, `/vendor/team`, `/vendor/verification`, `/vendor/payouts`, `/uploads`). Product image and shop image mutations accept only the `assetRef` returned by `/uploads` for the authenticated vendor and required purpose. Payout responses expose only masked payout destinations; the server never returns the encrypted account reference. Cart intentionally remains local on web/mobile: persist only product/variant IDs and quantities, then rely on authoritative checkout revalidation. Payment-status GET is side-effect free; poll only while its normalized status is `PENDING`, using controlled backoff, and stop at terminal status. Device registration supports iOS/Android push-token lifecycle only; push delivery is intentionally deferred.

Retries: GET requests are safe; checkout is idempotent using `Idempotency-Key` or `checkoutRequestId`. Product creation is explicitly non-idempotent until a durable request-key store is introduced, so clients must not auto-retry it. Payment initialization and report submission must not be retried without client-held idempotency state.

Vendor operations: dashboard reports completed-and-delivered sales, actionable orders, and items at or below the low-stock threshold. Analytics accepts `TODAY`, `7D`, or `30D`. Inventory lists bounded stock rows and accepts intent-based `INCREMENT`, `DECREMENT`, or `SET` adjustments; stock never goes negative. Product creation/update uses strict request schemas and never accepts tenant IDs or platform-owned fields. Upload first via `POST /uploads`, then submit its returned `storage://` asset reference in the matching product/shop mutation; foreign paths and external URLs are rejected.
